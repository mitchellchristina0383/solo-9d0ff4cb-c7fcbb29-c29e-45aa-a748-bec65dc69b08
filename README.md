# 内网 HTTPS 根证书更换顺序规划器

值班员更换内网 HTTPS 根证书时，用本工具先排好变更顺序：录入服务副本的新旧
PEM 证书链与终端批次的新旧 PEM 根证书包，工具用真实的 `openssl verify` 核验，
给出“每一步只换一个副本的链、或更新一批终端根包”的可行顺序；无解时区分
**证书材料无法通过验证** 与 **过渡名额不足** 两类原因并给出明细。

另附 **吊销核查页**（`/revocation`）：内网 CA 发来吊销清单（CRL）后，录入各
副本的叶子证书与直接颁发 CA 证书，逐副本判定 **已吊销 / 未列入 / 待核实**，
详见第 7 节。

## 1. 模型与规则

| 对象 | 状态 | 单步动作 |
| --- | --- | --- |
| 服务副本（1~4 个） | 旧链 / 新链 | 一次只把一个副本从旧链切到新链 |
| 终端批次（1~4 批） | 旧包 / 过渡包（新旧并集）/ 新包 | 一批终端可旧包直跳新包，也可先切并集过渡，再切新包 |

- 页面可设置**同时处于过渡态的批次上限** L（0 表示禁止并集过渡，只能直跳）。
- 任一核验时刻（初始态及每步动作之后），每批终端都必须只用**当时持有的根
  证书包**，按域名验证每个副本**当时出示的证书链**；全部 “批次 × 副本”
  组合通过，该状态才合法。
- 核验调用本机 `openssl verify -no-CAfile -CAfile <根包> -untrusted <中间证书>
  -verify_hostname <域名>`：信任锚仅来自录入的根包（不加载系统默认 CA），
  同时完成链签名/有效期校验与 SAN 主机名校验。
- 状态空间至多 2⁴ × 3⁴ = 1296，BFS 求步数最少的方案，动作顺序固定
  （开过渡 → 换副本链 → 收过渡/直跳），方案可复现。
- 无解诊断：
  - **硬无解**：现状（旧链×旧包）或目标态（新链×新包）本身核验失败，或放开
    名额到全部批次仍走不通；页面列出每个失败的“批次 × 副本”在全部 6 种
    链/包组合下的 openssl 失败原因（含主机名不匹配时叶子实际 SAN）。
  - **过渡名额不足**：放开上限可解、按当前 L 不可解时，二分求出最小所需名额，
    提示调大上限后重算。

## 2. 目录结构

```
app/
  certutil.py     # PEM 解析、并集合并、openssl verify 封装
  planner.py      # 状态建模、BFS 求解、无解诊断
  crlstore.py     # CRL 核验（颁发者/签名/编号/有效期/完整性）、并发安全持久化存储、快照
  revocation.py   # 逐副本吊销判定（已吊销/未列入/待核实）
  app.py          # Flask 路由（/、/revocation、/api/plan、/api/crl/* 等）
  templates/      # 单页界面 ×2（原生 JS，无前端构建）
  static/         # 样式
scripts/
  generate_samples.py  # 生成两套独立 PKI 的演示证书 + 吊销核查样例（CRL、同名换钥 CA）
samples/          # 已生成的样例（根/中间/各副本链/根包/revocation/两份 sample.json）
tests/            # pytest：求解器 13 项 + API 7 项 + 吊销核查 25 项
Dockerfile, docker-compose.yml
```

## 3. 启动方式

### Docker Compose（推荐）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

镜像内已安装 openssl，并在启动时确保 `samples/` 样例存在；含健康检查。

### 本地直接运行

```bash
pip install -r requirements.txt
python scripts/generate_samples.py samples   # 已随仓库生成，可重复执行
flask --app app.app run --host 0.0.0.0 --port 8000
```

## 4. 网页试跑流程

1. 打开页面后样例自动载入（3 个副本 × 3 批终端，默认过渡上限 3）；也可点
   “载入证书样例”重新载入。每个 PEM 输入框失焦后会显示解析概要（叶子 CN、
   SAN、链长 / 根包内证书数量）。
2. 点“求解变更顺序”，得到分步方案，每步附带动作后的状态快照与
   “本步核验 9/9 个组合全部通过”的核验证据，页面下方还有 6 列核验矩阵。
3. 试无解场景：
   - 把上限改成 0 → 提示“过渡名额不足，至少需要 3 个批次同时过渡”；
   - 把某批的“新根证书包”替换成旧根包内容 → 提示硬无解并列出 9 个失败配对
     及 `unable to get local issuer certificate`；
   - 把某个副本域名改成证书 SAN 之外的名字 → 提示 `hostname mismatch`
     （并附叶子实际 SAN）。

## 5. 实测结果

环境：Python 3.11 + OpenSSL 3.0.22。换证顺序规划部分共 **20 项全部通过**
（13 项求解器逻辑 + 7 项 Flask API；吊销核查 25 项见第 7.3 节），覆盖：

- 旧链仅被旧根信任、新链仅被新根信任、并集同时信任两者、域名不匹配必失败；
- 合法场景求出 9 步方案并逐步回放，验证每步只动一个对象、过渡名额不超限、
  每步全部核验通过、终态全部为新；
- L=0 多批次场景判为名额不足并求出最小名额 3，调到最小名额后可解；
- 新根包错放、现状即坏、SAN 不匹配均判硬无解且明细正确；
- 非法 PEM、空字段、非法上限、空表单均返回 400/抛错。

HTTP 端到端冒烟（真实 Flask 服务）四种返回：

| 场景 | status | 关键输出 |
| --- | --- | --- |
| 默认样例（L=3） | `plan` | 9 步，每步 9/9 核验通过 |
| L=0 | `insufficient_quota` | `min_required=3` |
| 新根包错放为旧根 | `hard_infeasible` | 9 个目标态失败项，原因 `unable to get local issuer certificate` |
| 域名与 SAN 不符 | `hard_infeasible` | `hostname mismatch（叶子证书 SAN: svc-a.internal.example）` |

另用 openssl CLI 直测样例链（旧包验旧链、并集包验新链、错误主机名拒绝）均符合预期。

## 6. 约束与余项

- 本机沙箱无 docker CLI，**Docker Compose 配置未在本机构建验证**；Dockerfile
  仅依据 python:3.11-slim 常规行为编写（显式 apt 安装 openssl、gunicorn 启动），
  请在有 Docker 的环境执行 `docker compose up --build` 复核。
- 证书核验通过每次请求临时文件调用 openssl 子进程完成；输入规模上限
  4×4、缓存按 PEM 组合去重，单次求解最多 96 次核验，实测秒级返回，未做
  高并发压测。
- 工具只做离线顺序规划与核验，不连接任何真实服务；换证顺序规划页不保存录入
  内容（吊销核查页的清单按设计持久化，见第 7 节）。
- 样例私钥仅用于本地生成演示证书，随生成过程只在 `samples/` 保留证书
  （脚本会在内存生成密钥，不落盘私钥文件）；请勿把样例证书用于任何真实环境。
- 证书链约定：叶子证书在前、中间 CA 依次在后的 PEM 拼接；根证书不放链文件，
  只放终端根包。

## 7. 吊销核查页（/revocation）

内网 CA 发来吊销清单后，值班员用本页查哪些 HTTPS 副本需要换证。

### 7.1 模型与规则

**上传清单**（`POST /api/crl/upload`，附颁发 CA 证书 PEM + 清单 PEM）：

- 只收 PEM 编码、覆盖该 CA 全部直签证书的**完整清单**：拒绝增量清单
  （含 Delta CRL Indicator）与 IssuingDistributionPoint 限定范围的清单；
- 逐项核对：**颁发者**（清单 issuer 与所附 CA 主题一致）、**签名**（用所附
  CA 公钥核验，支持 RSA/EC/Ed25519）、**编号**（CRL Number 扩展必须存在）、
  **有效期**（thisUpdate ≤ 上传时刻 ≤ nextUpdate）；所附证书必须是
  BasicConstraints CA=TRUE 且（若声明 KeyUsage）含 cRLSign 的 CA 证书；
- 按 **CA 名称＋CA 公钥** 保存最新清单：同名 CA 换钥后新旧清单各自独立，
  互不覆盖；数据落盘于 `data/crls/`（每清单一份 JSON，临时文件+rename 原子
  写入），**重启后保留**（compose 已挂命名卷 `crl-data`）；
- 单调替换：编号更大才替换；**编号更低、或同号但内容不同的上传一律拒绝
  （HTTP 409）并保留现行清单**；同号同内容可重传（幂等，返回 unchanged）；
- 并发安全：线程锁 + `fcntl.flock` 文件锁，锁内重新从磁盘加载后再做
  “比较-替换”，多线程与多进程（gunicorn 多 worker）并发上传都不会打破
  单调规则。

**核查**（`POST /api/crl/check`，每副本填叶子证书 + 直接颁发 CA 证书）：

- 每轮核查**开始时固定清单快照与核验时刻**，核查进行期间的新上传不影响
  本轮结果（下一轮生效）；
- 逐副本判定：**已吊销** / **未列入** / **待核实**，用到清单的行标明清单编号；
- 以下情况标 **待核实**：证书无法解析、**颁发关系验不过**（叶子颁发者与所附
  CA 主题不符，或叶子签名无法用所附 CA 公钥核验）、**找不到匹配清单**
  （按 CA 名称+公钥）、**清单在核验时刻已失效**（尚未生效或已过期）。

### 7.2 网页试跑流程

1. 打开 `http://localhost:8000/revocation`，样例自动载入 4 个副本
   （svc-a/b/c 用新中间 CA 的叶子，svc-a-old 用旧中间 CA 的叶子）；
2. 点“清单 #1（吊销 svc-b）”填入上传框 → 上传 → 已保存清单出现编号 1；
3. 点“开始核查”：svc-b **已吊销**、svc-a/svc-c **未列入**（编号 #1）、
   svc-a-old **待核实**（旧中间 CA 无清单）；
4. 再上传“清单 #2（吊销 svc-b、svc-c）”→ 编号更新为 2 → 重新核查：
   svc-c 变为**已吊销**，行内编号变为 #2；
5. 试传清单 #1 → 409“低于现行编号”；试传“同名换钥 CA 的清单 #1”→
   与原清单**并存**（列表中同名、公钥指纹不同），核查仍按原公钥匹配 #2。

### 7.3 实测结果（新增部分）

环境：Python 3.11 + cryptography 50 + Flask 3.1，`pytest tests/` 共 **45 项
全部通过**（求解器 13 + 规划 API 7 + 吊销核查 25）。吊销核查覆盖：

- 上传核验：颁发者不符、同名异钥签名失败、增量清单、过期/未生效、缺编号、
  非 CA 证书、多 CRL 块、垃圾 PEM 全部拒绝；
- 单调规则：stored → unchanged → 同号异内容拒绝 → updated → 低编号拒绝，
  每次拒绝后现行清单 DER 不变；
- 并发：6 线程 × 2 个 Store 实例（模拟多进程）混合上传，低编号与同号异内容
  全拒、同内容幂等、现行清单不变；空库并发首张恰好 stored 一次；多编号竞态
  最高编号胜出；
- 核查：样例三态判定、颁发关系两类失败与解析失败均待核实、过期/未生效清单
  待核实（注入核验时刻验证）；
- **核查中更新清单**：线程在快照后、判定前上传 #2，本轮仍按 #1 判定
  （svc-c 未列入 #1），下一轮按 #2（svc-c 已吊销 #2）；
- **同名 CA 换钥**：同名两张清单并存（指纹不同），换钥前后的叶子各自匹配
  对应清单，错配（旧钥叶子+新钥证书）判待核实；
- 持久化：新 Store 实例与新建 Flask 应用（≈重启）均能读到已保存清单，
  单调规则跨重启生效。

HTTP 端到端冒烟（真实 Flask/gunicorn 服务）：

| 场景 | 结果 |
| --- | --- |
| 上传 #1 → 核查 | svc-b 已吊销 #1，svc-a/svc-c 未列入，svc-a-old 待核实 |
| 上传 #2 → 核查 | svc-b/svc-c 已吊销 #2 |
| 重传低编号 #1 | HTTP 409，现行 #2 保留 |
| 同号同内容重传 #2 | HTTP 200 unchanged |
| 同名换钥清单 | 并存为第 2 张（同 CA 名、不同公钥指纹） |
| 进程重启 | 已保存清单全部保留 |
| 9 路并发（低编号/同号异内容/同内容） | 6×409 + 3×200，现行 DER 不变 |
| gunicorn 2 worker × 15 路并发（5 个编号） | 最高编号 #5 胜出，无规则违例 |

### 7.4 约束与余项（吊销核查）

- 本机沙箱无 docker CLI，**Docker Compose 配置（含 `crl-data` 卷）未在本机
  构建验证**；持久化目录默认为 `<仓库>/data/crls`，可用环境变量
  `CRL_DATA_DIR` 覆盖，compose 中已设为 `/app/data/crls` 并挂卷。
- 并发正确性依赖 `fcntl.flock`（POSIX）；多副本部署（多容器/多机）需换用
  共享存储或数据库行锁，当前实现保证单机的多线程+多进程安全。
- 清单有效期核对以上传时刻为准；已保存清单之后自然过期属预期，核查时会
  标“待核实（清单已过期）”，提醒值班员索取新清单。
- 不核验 CRL 的分发点与 CA 证书自身有效期/链上信任（内网 CA 证书由值班员
  当面取得，视为身份材料）；如需可后续叠加。
- 暂不提供清单删除接口；如需作废某 CA 的清单，目前需停服后删除
  `data/crls/` 下对应文件。
